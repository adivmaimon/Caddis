---
name: map
description: Build or refresh the codebase map - a script-generated import graph plus a short human map at .caddis/map/STRUCTURE.md covering what lives where, entry points, hubs, main flows and where new things go. Runs during init, when the map is stale, and in maintenance.
---

The map has two layers:
- **The graph** (`.caddis/map/graph.json`, `summary.md`): generated by `map.py` from real
  imports. A cache, gitignored, rebuilt on demand. It never guesses an edge.
- **The human map** (`.caddis/map/STRUCTURE.md`): written by you from the graph and the
  code. Committed. What a new engineer needs in their first hour. This is what other skills
  read first.

## 0. Install the script

`map.py` lives in this skill's `scripts/` folder. Copy it to `.caddis/bin/map.py` if that is
missing, or if `python3 .caddis/bin/map.py version` is older than the copy here. Every
Caddis skill calls it at that path, so the repo works without the plugin installed. It needs
only Python 3.8+.

## 1. Pick the mode

Run `python3 .caddis/bin/map.py status`.
- **No STRUCTURE.md**, or the user asked for a full map, or this is maintenance: **full**.
- **Stale**: **refresh**, covering only the areas it lists. If more than about a third of
  the source files changed, do a full map instead.
- **Fresh**: say so and stop.

## 2. Full map

1. `python3 .caddis/bin/map.py build` and read `.caddis/map/summary.md`.
2. Read the Accuracy section. If many imports went unresolved (a path alias or a layout the
   script missed), note it in Gotchas so nobody trusts a missing edge.
3. For each area, read its entry points and hubs, plus enough files to say what it is for
   (`map.py area <dir>` lists them). Don't read everything; sample.
4. Trace the two or three flows that matter most end to end: e.g. a request from route to
   database and back, a screen from tap to render, a job from trigger to result. Follow
   them with `map.py deps <file>`.
5. Write STRUCTURE.md using the template below.

## 3. Refresh

1. `python3 .caddis/bin/map.py status` lists the changed files and areas.
2. Read the changed files that are new, deleted or hubs. Skim the rest.
3. Update only the affected rows and sections of STRUCTURE.md. Add new areas, remove dead
   ones, fix flows that moved.
4. Replace the stamp line with the output of `python3 .caddis/bin/map.py stamp`.

## Template

Keep it under about 200 lines. For a large repo, keep this as the index and put detail in
`.caddis/map/areas/<area>.md`, one per big area, linked from the table.

```markdown
<!-- caddis-map commit: abc1234 -->
# <Repo> - Structure

> Generated with the Caddis map skill. The graph behind it: `python3 .caddis/bin/map.py`
> `uses <file>`, `deps <file>`, `area <dir>`, `orphans`.

## Areas

| Area | What it is | Key files |
| --- | --- | --- |
| `src/api` | API handlers, one file per resource | `router.ts`, `auth.ts` |

## Entry points
Where execution starts: app boot, server, CLI, workers, scripts. One line each.

## Hubs
Files most of the codebase depends on. Changing one is a wide change: check
`map.py uses <file>` first.

## Main flows
2 or 3 flows, each a short numbered list of files from trigger to result.

## Where new things go
| Adding | Goes in | Follow the pattern in |
| --- | --- | --- |
| A new screen | `app/` | `app/history.tsx` |

## Conventions
Naming, file layout, state, styling, error handling. Only what the code actually does.

## Gotchas
Generated code, circular imports, legacy areas, unresolved aliases, anything that bites.
```

## Rules

- Write only what you confirmed in the code or the graph. If something is unclear, say so
  in Gotchas rather than guessing.
- The stamp line must be the first line, from `map.py stamp`. Staleness checks read it.
- After writing, if the Commits section of `.caddis/caddis.md` lists scopes, check they
  still match the areas.
- Commit STRUCTURE.md as its own `docs:` commit with the `commit` skill, unless this ran as
  part of a plan, in which case it goes in that plan's commit.

## Using the map from other skills

- Before planning or changing code: read STRUCTURE.md, then `map.py status`. If stale for
  the areas you are working in, refresh first.
- Before changing a shared file: `map.py uses <file> --depth 2` for the blast radius.
- To place new code: the "Where new things go" table.
- Queries rebuild the graph automatically when the tree has moved on, so they are always
  current even when STRUCTURE.md is not.
